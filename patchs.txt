PARTE 2 — Melhorias propostas (roadmap priorizado)
Prioridade 1 — Alto impacto, aproveitam infraestrutura já existente
Busca híbrida vetorial + full-text via RRF ReciprocalRankFusion já funde múltiplos rankings por posição — só falta uma segunda fonte de ranking lexical (Postgres tsvector/GIN) fundida no mesmo array que o Retriever já monta. Ver arquivo anexo hybrid-search-skeleton.md para o esboço completo de contrato/código.
Streaming incremental real (SSE) em pelo menos um provider O contrato StreamingLanguageModel já existe e RagPipeline::stream() já sabe consumir AnswerDelta. Falta uma implementação que faça parse de text/event-stream chunk a chunk (OpenAI e Gemini suportam stream: true nativamente). Fecha a limitação mais visível do roadmap atual (OpenAILanguageModel é buffered, doc admite isso explicitamente).
Reranking com cross-encoder opcional Novo contrato Reranker::rerank(Question $q, list<VectorSearchResult> $results): list<VectorSearchResult>, aplicado depois da fusão RRF e antes de ContextSelector. Implementação via API (Cohere Rerank, Voyage) como primeira opção; cross-encoder local via ONNX Runtime como opção avançada. Historicamente é o maior ganho isolado de precisão em pipelines de RAG — maior que ajustar chunking ou top-k.
Decorator de retry/backoff para providers Mesmo padrão dos decorators de cache já existentes (CachedEmbeddingProvider/CachedLanguageModel): um RetryingEmbeddingProvider/RetryingLanguageModel com backoff exponencial + jitter para respostas 429/5xx. Resolve o ponto de fragilidade descrito no item 1.4 sem tocar no núcleo de concorrência.
Prioridade 2 — Diferencial competitivo (nenhuma lib RAG PHP concorrente tem hoje)
Harness de avaliação de RAG embutido RagEvaluator que roda um conjunto de perguntas-e-respostas "golden" contra o pipeline e reporta recall@k, groundedness e answer relevance. RetrievalDiagnostics/RagDiagnostics já coletam os dados necessários — falta só o harness de avaliação por cima.
Exportação OpenTelemetry dos diagnostics RagDiagnostics/RetrievalDiagnostics já capturam timing por etapa (queryPlanning, retrieval, fusion, expansion, selection, model) via hrtime(). Um adapter que emite isso como spans/métricas OTel torna a lib observável em produção com esforço mínimo — os dados já existem, falta o exportador.
Cache semântico de respostas CachedLanguageModel hoje cacheia por hash exato de mensagens. Um SemanticCache que reutiliza resposta se a nova pergunta está dentro de uma distância de cosseno configurável de uma pergunta já respondida (estilo GPTCache) reduz custo de LLM em produção de forma mensurável, e reaproveita EmbeddingProvider/VectorStore já existentes.
Prioridade 3 — Adoção e ecossistema
Bridge oficial para Laravel/Symfony (ServiceProvider/Bundle com config publicável) — reduz fricção de adoção para a maioria dos devs PHP que usam framework.
Loaders estruturados — Markdown com split por heading primeiro (formato mais comum de base de conhecimento interna), depois HTML/CSV/JSON.
CLI via Symfony Console para ingestão com barra de progresso, --dry-run e diff entre versões de documento — usa IngestionReport/ DocumentVersion que já existem, falta só a camada de apresentação.
Ordem de execução sugerida para o agente
Corrigir item 1.1 (duplicação) primeiro — é risco de manutenção ativo e barato de resolver.
Implementar item "Prioridade 1.1" (busca híbrida) usando hybrid-search-skeleton.md como guia.
Retomar os demais itens da Parte 1 (1.2, 1.3, 1.4) como tarefas pequenas e independentes.
Seguir Prioridade 1 → 2 → 3 do roadmap conforme capacidade.


examples/advanced-retrieval/ (ou equivalente) contendo exemplos independentes, como:

01-vector-search.php — demonstra apenas a busca vetorial.
02-lexical-search.php — demonstra apenas a busca lexical.
03-multi-query.php — mostra as consultas geradas pelo planejador heurístico e seus resultados.
04-rrf.php — exibe os rankings individuais e o ranking final após o Reciprocal Rank Fusion.
05-context-expansion.php — mostra a recuperação de chunks vizinhos.
06-hybrid-search.php — compara busca vetorial, lexical e híbrida usando a mesma pergunta.
07-diagnostics.php — imprime todas as estatísticas e diagnósticos do retrieval.
08-end-to-end-rag.php — executa o pipeline completo (planejamento → retrieval → RRF → expansão → seleção de contexto → LLM).

Cada exemplo deve:

ser executável diretamente com php examples/...;
imprimir claramente cada etapa do pipeline;
mostrar o tempo de execução, quantidade de documentos encontrados e chunks selecionados;
usar perguntas diferentes (conceituais, geração de código, identificadores como ERR_PAYMENT_1047, SKUs, classes, funções etc.);
ser amplamente comentado para servir também como documentação prática da biblioteca.
